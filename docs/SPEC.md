# YUZU Creator Studio(h3-creator-studio)仕様(第 1 版)

> 第 1 版の記述は当時の決定。その後の版(下の「第 2 版」「第 3 版」「第 4 版」)で変わった点はそちらが正しい(タブは 6 つ、MV・ショート動画・編集は実装済み)。

誰でも使える簡易な画像・動画・音楽の制作スタジオ。MiniMax-H3(動画+音声、静止画)、MiniMax-H3-Image(画像)、ACE-Step(音楽)、AivisSpeech(TTS)を 1 つの画面から使う。GPU には常に 1 つのエンジンだけを載せ、VRAM と CPU メモリを見ながら載せ替えるのがこのアプリの役目。

## 決めたこと

- 対象: ComfyUI の利用者。Windows を主に、Linux でも動く。NVIDIA GPU。
- 要件: VRAM の下限は設けない(6GB でも画角を絞れば動く)。推奨 12GB 以上。**CPU メモリ 32GB 前提**。NVMe 推奨。
- エンジン(すべて既存のリポジトリをそのまま子プロセスとして使う。中身には手を入れない):

| エンジン | 役目 | ポート | 準備確認 | GPU を空ける方法 | 起動(作業ディレクトリはエンジンのフォルダ) |
|---|---|---|---|---|---|
| `minimax-h3` | 動画(T2VA / FL2VA / Ref2VA)と静止画(T2I / Ref2I) | 8611 | `GET /api/status`(`busy` を含む JSON) | `POST /api/admin/unload`(実行中は 409)、戻すのは `POST /api/admin/reload` | `<venv>/python -u -m uvicorn app:app --host 127.0.0.1 --port 8611`。venv は `venv/` か `.venv/` |
| `minimax-h3-image-server` | 画像(T2I、参照編集) | 8633 | `GET /api/health`(`loaded`) | `POST /api/admin/unload`(409)、`POST /api/admin/load` | `.venv/python -m uvicorn app.main:app --host 127.0.0.1 --port 8633` |
| `ACE-Step-1.5-fast` | 音楽 | 8001 | `GET /health`(`data.models_initialized`) | **無い。プロセスを止める** | Linux `run_api_server_fast.sh`、Windows `run_api_server_fast.bat`。環境変数 `ACESTEP_API_HOST=127.0.0.1 ACESTEP_API_PORT=8001` |
| `AivisSpeech-Engine` | TTS(**CPU で動かす。GPU は使わない**) | 10101 | `GET /version` | 不要 | 配布版の実行ファイル `run`(Windows は `run.exe`)に `--host 127.0.0.1 --port 10101`。`--use_gpu` は付けない |

- エンジンの置き場所: 既定は `components/<名前>/`。`setup` が取り込む。既に別の場所にあれば、設定ファイルでそのフォルダを指すだけで使える(取り込みもモデル取得も飛ばす)。各エンジンは普通の git リポジトリのままなので、個別に起動も `git pull` もできる。
- 画面: 上段にタブ(画像・動画・音楽)。各タブは左に操作、右上に生成物を大きく、その下にそのタブで作ったもの。右側はギャラリーに切り替えられる(全て・画像・動画・音楽で絞り込み)。入力はすべてドラッグ&ドロップで、ファイルも、ギャラリーやタブの生成物も同じ操作で入力欄に落とせる。
- LLM(プロンプト強化、歌詞): 管理役が Gemma 4 E4B(llama.cpp の CUDA 版 `llama-server`)を 1 つだけ持つ。GPU で生成する直前に止め、生成中は起こさない(Easy Music の方式)。各エンジンの内蔵 LLM は使わない。
- 第 1 版で後回し: 認証、LAN 公開、複数 GPU、ジョブの同時実行、プリセット編集、リップシンク MV、LTX-2.5。

## 実装方針

1. 管理役は GPU を使わない FastAPI(Python 3.11+、依存は FastAPI / uvicorn / httpx / psutil / tomli 程度)。新規に書く。考え方は `diffusers-movie-server` のゲートウェイ(排他、unload、実行中は 409)を引き継ぐ。
2. 画面からエンジンを直接呼ばず、**管理役がすべて仲介**する(載せ替えを生成の手前で挟む、生成物を 1 つのギャラリーに集める、1 オリジンで済ませる)。
3. 画面は素の HTML + JavaScript + CSS(ビルド不要、Node 不要)。
4. 生成はすべて非同期ジョブ(投げて、ポーリング)。H3 動画の同期 API は管理役が裏で呼び、`/api/progress` で進捗を取る形に包む。
5. 生成物は `outputs/` に集め、台帳(SQLite 1 ファイル `outputs/studio.db`)に 種類・タブ・パラメータ・日時 を記録。ギャラリーは台帳を見る。
6. メモリ監視: nvidia-smi(2 秒おき)と各子プロセスの RSS(psutil)。Windows では共有 GPU メモリの増加(=VRAM あふれ)を見張って警告。
7. 載せ替えは 1 本の状態機械: 「今 GPU にいるエンジンを unload(ACE は停止)→ 空きを確認 → 次を起動 or reload → 準備完了を待つ」。
8. `setup.bat` / `setup.sh`: uv 導入 → エンジンの取り込み(既存は飛ばす)→ 各エンジンの setup 呼び出し → AivisSpeech 配布版(約 220MB の 7z)の取得。

## 作業の順序

1. 管理役の骨組み(設定、エンジンの起動と停止、準備確認、メモリ監視、載せ替えの状態機械)。画面はメモリ計とエンジンの状態表示だけ。
2. 画像タブ(H3-Image)。生成の流れとギャラリーの土台。
3. 動画タブ(H3: T2VA / FL2VA / Ref2VA / 静止画)と TTS。
4. 音楽タブ(ACE、簡単モード)と LLM。
5. `setup.bat` / `setup.sh`、README(エンジンの更新手順を含む)、Windows 実機での確認。

# 第 2 版(2026-11-22 に決定)

対象は **ジョブの同時実行**、**プリセット編集**、**リップシンク MV(MV タブ)** の 3 つ。複数 GPU・認証・LAN 公開・LTX-2.5 は引き続き後回し。エンジンの中身には手を入れない方針は変えない(エンジンへは環境変数と API だけで指示する)。

## 1. ジョブの同時実行

方針: **GPU に載るだけ載せ、載らなければ待つ。GPU を使わない仕事は待たせない。** 12GB では今までどおり エンジン 1 つずつ(載せ替えは自動)。大きな GPU では複数のエンジンを同時に常駐させ、別々のエンジンの生成を並行に走らせる。

- **レーン**: エンジンごとに 1 本(同じエンジンの仕事は 1 つずつ順番に)。GPU を使わない仕事(TTS、MV の音声分離・分析・結合)は CPU のレーン(既定 2 本まで同時)。ジョブの種類は使うエンジンと GPU を使うかを宣言する(既存の `Handler.component` / `Handler.gpu`、CPU の仕事は `component=None`)。
- **順番(公平さ)**: 受け付けた順に見ていき、始められるものから始める(後ろのジョブが空いているレーンで先に走るのは可)。ただし先頭で「GPU の空き待ち」になったジョブがあれば、そのジョブが降ろしたいエンジンに新しい仕事を入れない(後から来た仕事に追い越され続けないように)。
- **GPU の使い方の設定** `[gpu] mode`:
  - `exclusive`: 常駐は 1 エンジン(第 1 版と同じ)。
  - `share`: 複数のエンジンを常駐させる。各エンジンに VRAM の**利用枠**を割り当て、起動時に環境変数で渡す(H3: `H3_PROFILE`(利用枠に収まる最大の級)と `H3_VRAM_LIMIT_GB`、H3-Image: `H3IMG_VRAM_GB`、ACE: `ACESTEP_GPU_PROFILE`(14GB 以上 `16gb`、それ未満 `12gb`、10GB 未満は 8GB 向けの設定も))。
  - `auto`(既定): 総 VRAM 40GiB 以上なら `share`、未満なら `exclusive`。
- **利用枠**(share のとき): 既定は総 VRAM T に対して H3 = min(T×0.5, 48)GiB、H3-Image = min(T×0.35, 31)GiB、ACE = 14GiB。`[components.x] vram_budget_gb` で上書きできる。exclusive では利用枠を渡さない(エンジンが自分で全体を見て選ぶ。今と同じ)。
- **載せるときの判定**(エンジン X を ready にする): X が載っていれば何もしない。share では「常駐中のエンジンの利用枠の合計 + X の利用枠 ≤ 総 VRAM − 管理役の起動時に他のアプリが使っていた量 − 余白 1.5GiB」なら他を降ろさずに載せる。足りなければ、仕事中でない常駐エンジンを最後に使った時刻の古い順に降ろす(unload、できないエンジンは停止)。仕事中のエンジンを降ろさないと足りないときは、その仕事が終わるまで待つ(ジョブの表示は「GPU の空きを待っています」)。exclusive では常駐者を降ろして載せる(今と同じ)。
- **LLM**: 管理役の LLM は GPU の仕事を止めない。GPU に空きがあれば `--fit` で GPU も使い、GPU を使う生成中・載せ替え中は CPU だけで動かす(CUDA を隠して起動し直す)。歌詞・強化の API が「GPU で生成中」で断ることはなくなる(遅くはなる)。エンジンを載せる判定で LLM の VRAM が要るときは、LLM を CPU に移してから載せる。
- **画面**: 上段のメモリ計の下に、レーンごとの「実行中 / 待ち」と常駐中のエンジン(利用枠つき)を出す。ジョブには待ちの理由(順番 / GPU の空き待ち / エンジンの準備中)を出す。

## 2. プリセット編集

- **プリセット** = タブの入力欄の値(プロンプト・サイズ・秒数・STEP・モデル・ジャンルなど)に名前を付けて保存したもの。画像・動画・音楽・MV の各タブにある。
- 同梱のプリセット(リポジトリの `presets/*.json`、変更不可。複製して編集する)と、自分のプリセット(台帳 `outputs/studio.db` の `presets` 表)。
- 各タブの左上にプリセットの欄: 選ぶと入力欄に反映 / 「保存」(新規・上書き)/ 名前の変更 / 削除 / JSON の書き出し・読み込み。適用は入力欄を書き換えるだけで、生成はしない。参照画像などの生成物はプリセットに含めない。
- API: `GET /api/presets?tab=` / `POST /api/presets` / `PUT /api/presets/{id}` / `DELETE /api/presets/{id}` / `POST /api/presets/import` / `GET /api/presets/export?tab=`。

実装メモ(プリセットの実装で、上の記述から補った点):

- **同梱のファイル**は `presets/*.json`(配列か `{"presets": [...]}`。項目は `{tab, name, values}` で、ファイル名が tab ならそれが既定)。ID は `builtin:<tab>:<番号>`。読めないファイルと不正な項目は、警告を出して飛ばす(同梱の誤りで管理役を止めない)。同梱のプリセットへの PUT / DELETE は 400(複製してから編集)。`GET /api/presets` は、同梱(`builtin: true`)→ 自分のもの(作った順)。
- **値**は入力欄の値(文字・数・真偽値・それらの配列)の辞書で、JSON で 32KB まで。名前は 1〜60 文字。項目の名前は、ジョブの params と同じ名前を使い(`width` / `seconds` / `batch_size` など)、画面だけの選びは `mode` / `genre_mode`(音楽。`chip` か `free`)/ `genre` / `mood` / `vocal`。どの項目を持つかは、各タブの `getPresetValues` が決める(`seed` は、ランダムなら null)。
- **名前の重なり**: 新しく作る・読み込むときは「名前(2)」「名前(3)」…にする(同梱の名前とも重ならない)。名前の変更で重なるときは、番号を付けずに 409 で断る。読み込みは 1 件でも不正なら何も作らず、1 回 200 件まで。書き出しは `{"presets": [{tab, name, values}]}`(そのまま読み込める)。
- **反映**は、書かれている項目だけ(知らない項目は無視)。選択肢に無い値(読み込んでいないモデルなど)は入れず、「そのままにした項目」として知らせる。文字の欄(プロンプト・テーマ・歌詞・一言・人物の説明・曲の内容)は、プリセットの文が空でなければ置き換える(サイズだけのプリセットで、書きかけの文を消さない)。音楽のキャプションだけは、音の「型」なので空でも反映する(前のプリセットのキャプションを引きずらない)。
- **入れないもの**: 参照・フレーム・曲・キャラクター画像・読み上げ(TTS)の欄・生成中のプラン。MV の人物の説明・曲の内容は、曲や画像を落としたときに自動で入った文のままなら入れない(生成物の中身なので)。

## 3. リップシンク MV(MV タブ)

1 枚のキャラクター画像と 1 曲から、H3 の Ref2VA + Vocal Lock で口の合った MV を作る。既存の `Minimax-H3-lipsync-mv` は大きな GPU 向けのゲートウェイ(24GB 以上の構成)と外部の分離サービスを前提にしているためエンジンとしては使わず、その考え方とシーン分割の処理(Apache-2.0、同じ作者)を移植して、管理役の中で H3 エンジン(8GB でも Ref2VA + Vocal Lock が動く)を使って組み立てる。

- **入力**: 曲(音声の生成物かファイル。音楽タブの曲なら歌詞・テーマ・キャプションも引き継ぐ)、キャラクター画像(画像の生成物かファイル。画像タブの画像ならそのプロンプトを人物の説明に使う)、任意の説明(人物・世界観)、投稿先(横長 16:9 / 縦長 9:16 / 正方形 / 縦 4:5)、画質(高速 / 標準 / 高画質)、シーンの長さ(5〜10 秒)。
- **サイズ**: 横長 768×448 / 1024×576 / 1344×768、縦長 448×768 / 576×1024 / 768×1344、正方形 512×512 / 768×768 / 960×960、縦 4:5 512×640 / 640×800 / 768×960(高速 / 標準 / 高画質)。VRAM 16GB 未満の既定は高速。
- **流れ**(それぞれが 1 つのジョブで、MV の「制作」がつなぐ):
  1. `mv.analyze`(CPU): 音声を 44.1kHz に揃え、Demucs(htdemucs、CPU)でボーカルを分離し、無音・ボーカルの谷・ブレス・小節から 5〜10 秒のシーンに分ける(lipsync-mv の動的計画法を移植)。
  2. `mv.script`(LLM): シーンごとの演出を管理役の LLM が JSON で書き、H3 公式の Ref2VA 6 セクション形式に整形する(`<Subject 1>` = 画像の人物、ボーカル区間は `<Audio 1>: fully_copy` で口を合わせる。歌唱区間は正面か 3/4 向きのミディアムクローズアップ)。
  3. `mv.scene` × シーン数(H3): 画像とそのシーンのボーカルを参照に、Ref2VA + Vocal Lock(turbo 4 ステップ)。1 シーン終わるごとに次を入れるので、その間に他のタブの仕事が割り込める。
  4. `mv.assemble`(CPU): クリップをつないで、音声は元の曲に差し替えた MP4 にする。
- **歌わせない(イメージ MV、`lipsync = false`。2026-11-24 追加)**: mv_studio_V3 の「キャラクタイメージ MV」に当たる。V3 の実機プローブ(2026-08-26)で、口を動かすのは音声の参照そのもので、`vocal_lock=false` や閉口の指示では止められないと分かっているので、**H3 に音声を渡さない**ことで実現する。`mv.scene` は画像だけを参照に `seconds`(シーンの尺。音声が無いと H3 は尺を決められない)と `mute=true` で頼み、`mv.script` は歌の割合を見ずに「歌わない・口は閉じたまま」の演出を `<Audio 1>` の無い 6 セクション形式で書く。分析(分離・分割)はそのまま(切れ目にボーカルの谷を使う)。
- **制作の管理**: 台帳の `mv_projects` 表(入力、シーン、各クリップの生成物 ID、状態)。一時停止 / 再開 / 中止、失敗したシーンのやり直し、シーンごとの作り直し(プロンプトの編集・seed 変更)と再結合。管理役を再起動したら、途中の制作は一時停止として残る。
- **音声処理の道具**: Demucs と librosa は管理役の venv に入れず、`setup --mv` で `components/mvtools/.venv`(CPU 版 torch、約 1.3GB)を作り、そこで `studio/mvtools/` のスクリプトを子プロセスとして動かす。無ければ MV タブに案内を出す。
- **画面**: 左に入力、右上に制作の進み(シーンの一覧と各クリップ、最終の動画)、右下に MV の履歴(ギャラリーに切り替え可)。

実装メモ(MV タブの実装で、上の記述から変えた点・補った点):

- **制作の進め方**は、`mv.Director`(`studio/mv.py`)が「次にやること」を台帳のデータから導く(分析が無ければ分析、演出の無いシーンがあれば演出、できていない最初のシーン、結合がまだなら結合)。だから一時停止・再開・失敗・再起動のあとも、同じ規則で続きから進む。ジョブの終わりは `JobRunner.on_finished` で受ける。`resume` は一時停止・失敗に加えて、中止した制作からもできる。
- **シーンの境界は 24fps のコマの格子に載せる**(lipsync-mv の `quantize_scene_plan` の移植)。クリップは `round(尺 × 24)` コマちょうどに整え、最終の動画もその合計になる。H3 が丸めて短く返したときは、最後のコマを複製して足す(`tpad`)。
- **分析のやり直しでは、済んだ変換と分離を使い回す**(失敗後の再開で、数分〜数十分の分離をやり直さない)。分離の装置は `[mv] device`(空なら CPU)。
- **`mv.script` の JSON の修復は、会話に前の答えを足さず、同じ依頼に「JSON だけで答え直す」指示を足して頼み直す**(管理役の LLM は system と user の 1 往復だけ)。全体の構成(overview)が読めなくても、空のまま進める。人物の特徴は、画面の説明 → 画像の台帳のプロンプト → 画像を見て作った説明(下の「自動の説明」)→ 中立の文の順。
- **一時停止**は、走っているジョブは終わるまで続け、まだ始まっていない(順番待ち・準備中の)ジョブは取り下げて、次は入れない(他のタブの仕事の後ろで待っていたシーンが、順番が来てから勝手に始まらないように)。
- **シーンのやり直し**(`retry_scene`): プロンプトも seed も渡さなければ seed を取り直す(プロンプトだけなら seed はそのまま)。走っている制作でも、そのシーンを未生成に戻して、いまのジョブが終わった後に拾う。結合中と、そのシーンの生成中は断る。
- **結合し直しても、前の MV はギャラリーに残す**(`mv_<ID>.mp4`、2 回目以降は `mv_<ID>_2.mp4`…)。制作を削除しても、最終の MV は残る。
- MV のジョブは Director だけが入れる(`/api/jobs` の `tab` に `mv` は足していない)。
- **字幕・テロップを出さない**: すべてのシーンの指示に「字幕・キャプション・歌詞の文字・タイトル・クレジット・ロゴ・透かしを画面に重ねない」を必ず入れ、演出の LLM にも書かないよう指示し、書いてしまった文は取り除く(H3 には否定の指示が無い。2026-11-24 に利用者が MV の中の字幕を報告)。移植元の「No lyrics are written or inferred …」は、歌詞の文字を連想させるので「The sung content comes only from <Audio 1>.」に変えた。背景の文字(`background_text`)は MV タブで選べる。
- **人物の見た目の整理**: `mv.script` の最初に、人物の説明(画面の入力か画像のプロンプト)から LLM で見た目だけ(subject / face / hair / outfit / style)を抜き出して使う。画像のプロンプトには場所・光・ポーズも書かれているため、そのまま人物の定義に入れると全シーンがその場面に縛られた(2026-11-22 の実機で、窓辺の画像の MV が 5 シーン中 4 つ同じ部屋)。抜き出せなければ説明をそのまま使う。
- **自動の説明(画像から人物の説明・曲から曲の内容)**: 外から持ち込んだ画像・曲は、台帳に画像のプロンプトも曲のテーマも無く、人物の説明と曲の内容・世界観が空のままで演出が一般的になる。そこで、各欄の横の「🔍 画像から作る」「🎧 曲から作る」で欄を埋められるようにした(確かめて直してから作れる。自動で入れた文の印を付けるのでプリセットには入らず、書いた文は確認なしには置き換えない)。空のまま「MV を作る」を押しても、制作の中で同じことが自動で走る。どちらも管理役の LLM(Gemma 4 E4B)の画像・音声の入力を使い、GPU も ACE-Step も使わない。
  - **画像 → 人物の説明**(`POST /api/mv/describe/image`、`studio/mvdescribe.py` の `describe_character`): llama-server に投影ファイル `mmproj-gemma-4-E4B-it-Q8_0.gguf`(同じ HF リポジトリ、約 0.56GB。画像と音声の入力を持つ)を `--mmproj` で付けて起動し(あれば CPU 専用でも付ける。無ければ画像・音声を頼まれたときに 1 回だけ取得する。読み込めずに終了したら投影ファイルなしで起動し直すので、テキストの chat は止まらない)、`Llm.chat_image` が画像(長辺 1024 に縮める)を data URI で送る。プロンプトは lipsync-mv の `analyze_character`(subject / face / hair / outfit / style / identity_anchor の JSON)に、「見た目だけ(表情・場所・光・ポーズ・動作は除く)」と、欄に入れる日本語の 1 行 `description_ja` を足したもの。CPU 専用で 1 枚 10〜15 秒。画像を読めなければ台帳のプロンプトから(`mvscript.character_facts`)、それも無ければ空(`source` = `vision` / `prompt` / `default`、理由は `note`)。
  - **曲 → 曲の内容**(`POST /api/mv/describe/song`、`listen_song` と `propose_concept`): 音楽タブの曲は、聞かずに、台帳の params から LLM が案を書いてその場で返す(`source: "params"`)。外から持ち込んだ曲は、曲の 30 秒を最大 2 か所(40 秒以下は先頭の 1 か所、長い曲は長さの 25% と 60% の位置から。近すぎれば 1 か所)を ffmpeg で 16kHz モノラルの WAV に切り出し(`mv_audio.cut`)、`Llm.chat_audio` が OpenAI 互換の `input_audio`(WAV)で 1 か所ずつ聞かせる(2 か所を 1 回で聞かせると先頭の方だけを答えがちだった)。答えは JSON `{language, genre, mood, instruments, vocal, tempo}`(genre・mood・instruments は配列でも文字列でも読む。読めなければ 1 回だけ頼み直す)で、2 か所の答えを項目ごとに混ぜて(同じ語は 1 つに)、LLM が日本語 2〜3 文の案にする(`source: "listen"`、`listen` に聞き取り)。CPU 専用で 1 か所 12〜13 秒、2 か所の曲は案まで 30 秒ほど。**歌詞は聞き取らず、案にも使わない**(精度が分からず、歌詞を推測しないのが MV の方針)。聞き取りは小さなモデルの当て推量なので、案の材料としては「おおよそ」と伝え、歌い手の性別・見た目は案に書かせない(人物は画像で決まる)。同期の API(画像と同じ。ジョブにはしない)で、画面に「曲の聞き取り(参考)」として閉じて出す。
  - **制作の中**: 人物の説明が空なら `mv.script` の最初に画像から作って残す(`character_source` = `vision`。読めなければ `none` と `character_note`。再開でやり直さない)。曲の内容が空で曲に台帳の情報が無いときは、作成時に `listen = "pending"` を置き、`next_step` が分析のあとに `("listen",)` を返す(`mv.listen`。CPU のレーンで、LLM が曲を聞いて案を書き、`concept`・`concept_source` = `listen`・`listen = "done"` を書く。BPM は分析の librosa のもの)。音楽タブの曲は今までどおり `concept_from_song` で、聞く段は入らない。**聞けなくても MV は止めない**: `mv.listen` が失敗したら(音声を読めない・ffmpeg が無い、など)、`listen = "skipped"` と理由(`listen_error`)を残し、曲の内容なしで続ける。制作の画面は、どの説明が自動か(`sources`)と理由(`source_notes`)を出す。

# 第 3 版(2026-11-24 に決定)

対象は **ショート動画(ショート動画タブ)**: 曲の長さ程度(目安 5 分、上限は GPU 次第)の、物語性のある短い動画を作る。MV タブの仕組み(制作 → 分析 → 演出 → シーン × N → 結合、一時停止・やり直し・再起動後の続き)を土台にし、変わるのは「時間軸の決め方」「参照の渡し方」「音の扱い」。LTX-2.5 は引き続き使わず、H3 だけで作る。story-studio(脚本・出演者・場所の階層を持つ本格版)の簡易版で、横断的な概念(複数の出演者・場所の台帳)は持たない。

## 1. 入力(ショート動画タブ)

- **物語・映像のイメージ**(文章。曲もセリフも無ければ必須、あれば任意): 何を描くか。LLM が全体の筋とシーン割りを書く材料。
- **曲**(任意。音楽タブの曲・ギャラリー・PC のファイル): あれば BGM。
- **セリフ・ナレーション**(任意。文章): あれば AivisSpeech で読み上げ、人物がそれに口を合わせる(lipsync-mv のナレーションモードと同じ方式)。欄の横の「📝 物語から作る」で、物語の文章から LLM にナレーションの案を書かせられる(確かめて直してから作る。空のまま作るときは、セリフなしの動画)。話者は AivisSpeech の一覧から選ぶ(動画タブの TTS と同じ)。
- **参照画像**(0〜4 枚。画像タブの画像・ギャラリー・PC のファイル): 1 枚ごとに役割を選ぶ — **人物**(全シーンに同じ人物。`<Subject 1>`)か **景色・物**(その場所・物を出すシーンの参照)。人物は 1 枚まで(複数の出演者は持たない。story-studio の領分)。セリフがあるときは人物の画像が必須(口を合わせる相手)。
- **長さ**: 曲があれば曲の長さ、セリフがあれば読み上げの長さ(曲とセリフの両方があれば読み上げの長さ。曲は BGM として下に敷く)、どちらも無ければ利用者が指定(30 秒〜。既定 60 秒)。**5 分を超えるときは警告**(A4000 の高速で 1 シーン約 3.5 分 → 5 分の動画で 2〜3 時間。PRO 6000 / 5090 ならその数分の 1)。上限は 3600 秒(1 時間。それ以上は受け付けない。シーンが多いと画面の操作が重くなる)。
- 投稿先・画質・シーンの長さ(5〜10 秒)・背景の文字・seed は MV と同じ。字幕・テロップは出さない(MV と同じ規則)。**セリフのテロップ(字幕)**(2026-11-24 に追加): `subtitles`(既定 false)。lipsync-mv の `subtitles.py` を `studio/mvsub.py` に移植し、結合で sentences.json(文の時刻)から ASS と SRT を作り、ffmpeg の `ass` フィルタで焼き込む(映像は H.264 crf 18 で作り直す。音声なしのときは焼き込みだけ)。SRT は最終の動画の隣(`short_<ID>.srt`)に置き、台帳の params(`srt`)から画面がリンクを出す。結合し直しで付け外しできる。字体は `[mv] subtitle_font`。
- **最終の音声**(結合の設定。後から変えて結合し直せる): 自動(下の規則)/ **音声なし**(映像だけの MP4。他のツールで音を付ける人向け)。

## 2. 時間軸とシーンの決め方

| 入力 | 時間軸 | シーンの切り方 | シーンの音 |
|---|---|---|---|
| セリフあり(曲は任意) | 読み上げ音声 | 文の切れ目(TTS の文ごとの時刻)で 5〜10 秒に束ねる(`mv_audio.analyze` に文の境界を渡す。Demucs は使わない: 読み上げはそのままボーカル) | Ref2VA + Vocal Lock(人物の画像 + そのシーンの読み上げ)。口を合わせる |
| 曲だけ | 曲 | MV と同じ(Demucs で分離、谷・息継ぎ・小節) | `mute` で作り、結合で曲に差し替え(MV の歌わせないと同じ) |
| どちらも無し | 指定の長さ | LLM が物語から 5〜10 秒のシーンに割る(`short.plan`。合計が指定の長さになるよう、コマの格子に丸める) | H3 が作る音(環境音・効果音)をそのまま残す |

- セリフありのシーンでも、物語の都合で人物が映らないシーン(景色だけ)は作れない(読み上げは全編を通して流れ、口を合わせる人物が要る)。人物のいないカットを混ぜたい物語は、セリフなし + 曲、または音声なしで作って、他のツールでナレーションを足す。
- 曲 + セリフ: 読み上げが時間軸。結合で、読み上げを主、曲を BGM(-14 dB、読み上げの前後で自然に収まるよう曲の長さに合わせて切り、末尾 2 秒はフェード)として混ぜる。曲が読み上げより短ければ曲を繰り返さず、そこで BGM は終わる(繰り返しは不自然になりやすい)。

## 3. 参照の渡し方(H3)

- 参照なし → `/api/t2va`(プロンプトだけ)。
- 人物あり → `/api/ref2va`。`<Picture 1>` = 人物。MV と同じ `<Subject 1>` の定義と保持。
- 景色・物あり → `/api/ref2va` の参照に加える(`<Picture n>`)。そのシーンの演出がその場所・物を使うときだけ渡し(LLM がシーンごとに「使う参照」を選ぶ)、保持は `partially_preserved`(配置・雰囲気・主要な物は保つが、カメラや時刻は変えてよい)。人物も景色も使わないシーンは t2va。
- 尺は常に `seconds` で明示(セリフありは読み上げの長さに合わせるので送らない。MV の歌わせると同じ)。

## 4. 演出(LLM、`short.script`)

1. **筋**(1 回): 物語の文章(+ 曲の内容、セリフの文)から、タイトル・舞台・登場人物(人物の画像があればその見た目を固定)・起承転結・場面の一覧を JSON で書く。
2. **シーン割り**(どちらも無しのときだけ、`short.plan`): 筋と指定の長さから、各シーンの秒数(5〜10)と場面を決める。曲・セリフのときは分析の切れ目をそのまま使い、各シーンに場面を割り当てる。
3. **シーンごとの演出**(BATCH_SIZE ずつ、MV と同じ): 使う参照(人物 / 景色の番号)、構図、動き、光、感情。セリフのシーンは MV の歌唱と同じ規則(口が見える構図、`<Audio 1>` に合わせて発話)。セリフのない人物のシーンは口を閉じる。前後のつながり(同じ場所・時刻・服)は continuity_rules で持たせる。
4. 最終の形は H3 公式の 6 セクション形式(t2va は参照の節を持たない形)。

## 5. 画面・データ

- **ショート動画タブ**(5 つ目のタブ)。左に入力、右上に制作の進み(シーンの一覧。多いときはスクロール。5 分超は作る前に警告)、右下に履歴。MV タブの画面の複製から始め、共通の仕組み(シーンの行・ボタン・結合し直し)は `web/mv.js` から切り出して共用する。
- 台帳は `mv_projects` 表をそのまま使い、`kind`(`mv` / `short`)列を足す。Director も共用(「次にやること」の規則に `short.plan` と、分析の有無の分岐を足す)。ハンドラは `studio/handlers/short.py`(analyze / tts / plan / script / scene / assemble)。読み上げは動画タブの TTS と同じ `studio/tts.py` を使う(AivisSpeech は CPU。GPU の切り替えは不要)。
- 最終の動画は `outputs/video/short_<ID>.mp4`(結合し直しは `_2`…)。「音声なし」で結合したものも別名で残す。
- プリセット: ショート動画タブにも(投稿先・画質・長さ・話者・最終の音声)。

# 第 4 版(2026-11-24 に決定)

対象は **編集タブ**: ギャラリーの動画・画像・曲を、GPU を使わず ffmpeg だけでつなぎ・切り・色を変え・音を差し替える簡易編集。MV・ショート動画の制作(Director)とは別の、軽い仕組み。やらないこと(第 1 版): 字幕の入力、速度の変更、ピクチャインピクチャ、音量の細かい調整、キーフレーム、マウスで引くタイムライン。

## 1. 編集プロジェクト(非破壊)

元の動画は一切触らない。プロジェクトは **状態(state)** の JSON と、その **履歴**(元に戻す / やり直す)。書き出しのたびに ffmpeg で作る。

```
state = {
  "clips": [ {"id": 生成物の ID, "kind": "video" | "image", "in": 秒, "out": 秒, "duration": 秒(image は指定、既定 3)} , ... ],
  "transitions": [ {"after": クリップの添字(その後ろの境目), "type": "cut" | "crossfade" | "fadeblack", "duration": 秒(0.5〜2)} ],
  "fade_in": 秒 | 0, "fade_out": 秒 | 0,
  "effects": [ {"type": 色調(mono / sepia / warm / cool / vintage / vignette / negate / blur)| 調整(saturation / contrast / brightness)
                | 選択区間の効果(fade_to_black / fade_from_black / black / fade_to_white / fade_from_white / zoom_in / zoom_out / pan_* / zoom_in_right / zoom_in_left。区間が必須),
                "value": 数(調整とズーム・パンの倍率。他は null), "start": 秒 | null, "end": 秒 | null} ],   # 区間はプロジェクト全体の秒数。null は全体
  "audio": {"mode": "original" | "music" | "mix" | "none", "song_id": str | null, "song_db": -14},
  "width", "height", "fps"      # 先頭のクリップから(画像だけなら 1024×576 / 24)。違う動画は縮めて黒縁(pad)
}
```

- **時間の指定**は、すべてプロジェクト全体の秒数(効果の前の、クリップをつないだだけの時間軸。クロスフェードで縮む分は書き出しのときに計算する)。
- **区間の削除**(`delete_range(start, end)`)と **挿入**(`insert(at, 生成物, duration)`)は、該当するクリップをその位置で分けて(同じ生成物の in/out を変えた 2 つのクリップ)入れ替える。境目の効果は、分けたところには付かない(cut)。
- **元に戻す / やり直す**: 操作のたびに state を履歴(`history`、最大 100)に積む。`undo` は 1 つ戻し、`redo` は進める。履歴は台帳に残す(再起動後も戻せる)。
- 操作は API の 1 回 = 履歴 1 段(`PUT /api/edit/{id}/state` で state 全体を置き換える。画面が state を組み立てて送る。サーバは検証して、履歴に積む)。

## 2. 書き出し(ffmpeg、CPU のレーン)

- **プレビュー**: 操作のあと、画面が `POST /api/edit/{id}/preview` を呼ぶ(ジョブ `edit.preview`、CPU)。短辺 480 の軽い MP4(crf 28、音声 AAC 96k)を `outputs/edit/<ID>/preview_<N>.mp4` に作って返す(ギャラリーには載せない。古いプレビューは消す)。操作が続いたら、走っているプレビューは中止して新しいものを入れる。
- **書き出し**(`POST /api/edit/{id}/export`、ジョブ `edit.export`): 元の解像度の MP4(crf 18、音声 AAC 256k)を `outputs/video/edit_<ID>.mp4`(2 回目以降 `_2`…)に作り、ギャラリーに載せる(tab = edit、params に state の写し)。
- **ffmpeg の組み立て**(`studio/editclip.py`。純粋な関数、テストしやすく):
  1. クリップごとに `trim` / `setpts`、画像は `loop` で duration 秒、`scale` + `pad` でプロジェクトの寸法、`fps`。音声は `atrim`、無ければ無音(`anullsrc`)を足して長さをそろえる(クリップはみな音声ストリームを持たせ、後の `concat` / `xfade` / `acrossfade` が崩れないように)。
  2. 境目: cut は `concat`、crossfade は `xfade=transition=fade:duration=d:offset=…` + `acrossfade`、fadeblack は `xfade=transition=fadeblack`。xfade は 2 入力ずつ左から畳む(offset は累積の長さ − d)。
  3. 効果: `eq=saturation=…:contrast=…:brightness=…`、mono は `hue=s=0`、fade_to_black は `fade=t=out:st=…:d=…` または `eq=brightness=-1` の区間。区間は `enable='between(t,start,end)'`(クロスフェードで縮んだ分は、境目の前後で時刻を直して渡す)。先頭 / 末尾の `fade=in/out`。
  4. 音声: original はつないだもの、music は曲(先頭から、長さで切り、末尾 2 秒フェード)、mix は `amix`(曲 -14dB、ショート動画の mix と同じ)、none は `-an`。
- **長い動画**: 書き出しは数分かかりうる。進捗は ffmpeg の `-progress pipe:1` の `out_time` で出す(mv_audio._run_ffmpeg を進捗つきにする)。

## 3. API・台帳・画面

- 台帳: `edit_projects` 表(id, created_at, updated_at, name, state_json, history_json, cursor, preview, output_id)。
- API: `GET /api/edit`(一覧)、`POST /api/edit`(新規。名前)、`GET /api/edit/{id}`、`PUT /api/edit/{id}/state`、`POST /api/edit/{id}/undo`、`/redo`、`/preview`、`/export`、`DELETE /api/edit/{id}`、`PATCH /api/edit/{id}`(名前)。検証(日本語の ValueError): 生成物が動画・画像・曲か、in < out ≤ 長さ、区間がプロジェクトの長さの中、効果の値の範囲(彩度 0〜3、コントラスト 0〜3、明るさ -1〜1)、境目の効果の長さ ≤ 両側のクリップの半分。
- ギャラリーの削除の保護: 編集プロジェクトの state が使っている生成物は消せない(MV と同じ `_in_use`)。
- **画面(編集タブ、6 つ目)**: 左に 1) プロジェクトの選択・新規・名前、2) クリップの列(ギャラリー・PC のファイルをドロップで末尾に追加。各行: サムネイル、in/out の欄、長さ、▲▼で並べ替え、×)、3) 区間(開始・終了の秒。プレビューの再生位置から「ここから」「ここまで」)、4) 操作: 区間を削除 / 位置に挿入(ドロップ欄 + 画像の秒数)/ 色調(見た目: モノクロ・セピアなど)/ 調整(彩度・コントラスト・明るさ)/ 選択区間の効果(フェード・黒・白・ズーム・パン。区間に効く)/ 境目の効果(境目ごとの選びと秒数)/ 先頭・末尾のフェード / 音声(4 つの選び + 曲のドロップ)、5) 元に戻す・やり直す・書き出し。右上にプレビュー動画(操作のたびに作り直し。作っている間はぼかし + 進み)と、効果・境目を帯で示す簡単な目盛り(クリックで再生位置)。右下に編集プロジェクトの一覧と、書き出した動画(ギャラリーに切り替え可)。
- プリセットは無し(編集は素材ごとに違う)。

実装メモ(第 4 版。上の記述から変えた点・補った点):

- **view に `error`**(最後に入れたジョブの失敗の理由。`job` はジョブが終わると null になるので、プレビューの失敗を画面が知るため)。
- **`validate_state` は正規化した state を返して、それを保存する**: 数は小数 3 桁、画像は in=0 / out=duration、cut の境目は捨てる、幅・高さ・fps は先頭の動画から決め直す(画面の値は見ない。画像だけなら 1024×576 / 24)。
- **ジョブの params は `{"project_id", "state"(頼んだときの写し), "seq"}`**: 順番待ちの間に編集が続いても、頼んだ状態で書き出す。
- **クロスフェードの組み立て**: カットでつながる並びを 1 つの `concat` にまとめ、そのまとまりを左から `xfade` / `acrossfade` で畳む。`concat` の後に `fps` を 1 段挟む(`concat` の出力の timebase が 1/1000000 で、`xfade` が合わない。ffmpeg 6.1 で確認)。入力は `-ss` / `-t` で必要な範囲だけ読む。音声の無い動画は ffprobe で見て `anullsrc` で埋める。
- **分割・削除・挿入**(`editclip.split_at / delete_range / insert_at` と、画面の `EDIT_LOGIC` の同じ処理): 効果の区間は中身に合わせてずらす・縮める。境目の効果は両隣のクリップの半分までに縮め、0.5 秒を割れば捨てる。0.1 秒未満の切れ端は作らない。境目から 0.1 秒以内の挿入は境目に寄せる。
- **効果の区間と境目**: 境目に始まる区間は後ろのクリップ、境目で終わる区間は前のクリップに属する。クロスフェードで縮む分は、書き出しの時間軸に直してから `enable` に渡す。
- **プレビューと書き出しは同時に走れる**(view の `job` は書き出しを優先)。プレビューは新しい要求が来たら走っているものを中止して入れ直す。
- **確認(2026-11-24)**: 灯台の MV 8 秒 + 少女 6 秒をクロスフェード 1 秒でつなぎ、2〜5 秒をモノクロ、曲に差し替え → プレビュー 13 秒。1〜3 秒を削除(11 秒)→ 元に戻す(13 秒)→ やり直す → 4 秒の位置に画像 2 秒を挿入(黒縁)→ 書き出し 312 コマ(13.0 秒)。画面でも、クリップの列・目盛り・色調・境目・音声の欄と「作り直す」を確認。
- **プレビューは状態の指紋つきの名前で新しい順に 8 本残す**(`preview_<N>_<指紋>.mp4`)。元に戻す・やり直すで、その状態のプレビューが残っていれば作り直さずにそれを出す(2026-11-25、利用者の報告: 戻るを 2 回押すと「古い版です」が出ていた)。
- **選択区間の効果**(2026-11-25 に追加、境目の効果とは別の欄): 黒へ / 黒から / 白へ / 白からフェード(`fade` に `enable` を付け、区間の外は元のまま。以前の「黒に落とす」は区間の後も黒のままだったが、これに置き換えた)、黒にする(`drawbox=t=fill`)、ズームイン / アウト(倍率 1.05〜2。`scale` の `eval=frame` でコマごとに拡大してから中央を元の寸法で `crop`。`crop` の w/h は起動時に 1 回しか評価されず `t` を使えないので、`zoompan` でも `crop` でもなくこの形)。境目の効果には「区間の境目に適用」(区間の中の境目すべてに、区間の長さ 0.5〜2 秒で)。
- **このコマを画像に**(`POST /api/edit/{id}/frame {t}`、同期): プレビューの再生位置(export の秒)に映っているクリップと元の動画の秒を `editclip.source_at` で求め、元の動画から元の解像度で 1 コマを PNG に抜いてギャラリー(画像、tab = edit、params に source_id / source_s / project_id)に載せる。効果は掛けない。静止画のクリップならその画像の行を返す。

# 見直し(2026-11-25)で変えたこと

アプリ全体の見直し(バックエンド・画面・文書の 3 方向)で見つけた不具合の修正。SPEC の記述との差分:

- **ギャラリーの削除の保護**は、MV・ショート動画の制作が「完成・中止」でも、その曲と画像を消せない(やり直し・再開・結合し直しで要るため)。理由にはその制作の題を出す。編集プロジェクトの保護は従来どおり。
- **ショート動画の長さ**は 30〜3600 秒。`min_s` / `max_s` / `length_s` / `seed` は NaN・無限大を断る。
- **編集の fps** は、この版以降に登録した動画(台帳の `outputs.fps`、ffprobe の avg_frame_rate)から決める。それより前に登録した動画は fps が無く 24 のまま。MV・ショート動画の最終の動画は 24。
- **編集のズーム・パン**は、プレビュー(短辺 480)でもその寸法で切り出す(以前はプロジェクトの寸法で crop していて、短辺 480 超のプロジェクトのプレビューが失敗した)。値の無いフィルタ(`negate`)の区間は `negate=enable=…`。
- **テロップの ASS のパス**は ffmpeg の 2 段のエスケープ(フィルタの引数 → フィルタグラフ)。Windows の `C:\…` で失敗していた。
- **このコマを画像に**は、クリップの最後のコマを超えない時刻に丸める。
- **`/api/jobs`** は登録済みの `h3image.*` / `h3.*` / `ace.*` だけを受ける(`mv.*` / `short.*` / `edit.*` は Director・EditManager だけが入れる)。編集ジョブの normalize は state を検証し直す。ジョブの表には編集の state の指紋だけを残す(state 本体はメモリのジョブに)。
- **ffmpeg の実行**(MV・ショート動画の結合、切り出し、変換)は Popen で、中止で止められる。待ち時間は `max(600, 20 × 尺)` 秒。
- **共有モード**の載せる判定は、まだ載っていない busy のエンジンの利用枠を数えない(2 つの準備中ジョブが互いを待って止まっていた)。他の GPU エンジンが busy の間は、他のアプリの使用量(baseline)を測り直さない。
- **外部で動いていたエンジン**が終了していたら(unload も health も答えない)、停止扱いにして続ける。AivisSpeech は読み上げのたびに生存を確かめる。
- **プロンプト強化**は、GPU エンジンを載せる前に LLM の VRAM を手放す(GPU ジョブと同じ)。
- **起動時**に `outputs/` の `*.part` を消す。生成物の削除は隣の `.srt` も消す。エンジンのログは起動時に 50MB を超えていれば末尾 1MB だけ残す。
- **`/api/status`** に `shared_gpu_total_mib`(Windows: CPU メモリの半分。他は null)。
- **画面(編集)**: 分割・削除・挿入はサーバと同じ最短 0.1 秒の規則(それ未満の切れ端は作らず、境目から 0.1 秒以内の挿入は境目に寄せる)。区間の欄は小数 3 桁。フェードの合計は書き出しの長さまで。ジョブの失敗の理由(`view.error`)を出す。プロジェクトが消えたらポーリングを止める。操作は順に待たせる(取りこぼさない)。古い応答で新しい表示を上書きしない。幅 900px 以下は 1 列。
- **画角・画質(2026-11-25)**: 「投稿先」を「画角」に改名。画角に 横 4:5(`5:4`)と 手動入力(`custom`: width / height を 256〜1344、32 の倍数に丸める。画質の欄は使わない)、画質に 低 VRAM(`low`: 長辺 512。16:9 512×288、9:16 288×512、1:1 384×384、4:5 416×512、5:4 512×416)を追加。MV とショート動画で共通(`mv.resolve_format`、`web/project.js` の `videoSize`)。
